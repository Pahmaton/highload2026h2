# Расчётно-пояснительная записка для курсовой работы по предмету "Проектирование высоконагруженных систем"

## 1. Тема и целевая аудитория

### Тип сервиса

Цифровой банк без отделений, по образцу Т-Банка. Аналоги в России: Озон Банк, Яндекс Банк. В мире: Revolut, Nubank, Monzo, Chime.

### Ключевой функционал (MVP)

- Регистрация и вход (по номеру телефона, подтверждение кодом, затем вход по PIN-коду или Face ID)
- Счета и карты (баланс, лента операций с дозагрузкой, поиск и фильтры по истории)
- Переводы по номеру телефона (внутри банка и через СБП)
- Вклады (открытие, пополнение, начисление процентов, закрытие)
- Кредиты (заявка, оценка кредитоспособности, выдача на счёт, график платежей и списание по графику)
- Push-уведомления по каждой операции

### Ключевые продуктовые решения

- Отделений нет, поэтому недоступность API равна недоступности банка
- Баланс считает только сервер, клиент его не кэширует и не пересчитывает
- Списание в два шага: удержание при покупке и списание по подтверждению от магазина
- Получатель перевода определяется по телефону через запрос в СБП прямо в момент операции
- Проценты по вкладам и кредитам начисляются раз в сутки, не в реальном времени. Ежемесячные платежи по кредитам списываются ночью
- Кредитный скоринг асинхронный: клиент подаёт заявку, решение приходит позже push-уведомлением

### Целевая аудитория

Россия, 34 млн MAU, 15,4 млн DAU (II кв. 2026, [[1]](https://cdn.tbank.ru/static/documents/724f5d58-cb93-443b-a7eb-72da6d42fe74.pdf)). Клиентская база банка 54,9 млн [[2]](https://cdn.tbank.ru/static/documents/afa4c849-6d6f-4b5c-bb22-b03f471fe18b.pdf). Аудитория распределена по 11 часовым поясам, но около 80 % населения живёт в зонах UTC+3 - UTC+5.

### 2.2. Продуктовые метрики

Платежи считаем через долю банка на рынке: 243 млн платежей в сутки x 1/6 = 40,5 млн платежей в сутки, или 40,5 / 15,4 = 2,63 на DAU. Доля известна по объёму в рублях, а применяется к количеству: допускаем, что средний чек клиентов банка близок к среднему по рынку. Каждый платёж - две операции: удержание суммы при покупке и списание после подтверждения магазина; в ленте операций это одна запись.

Переводы считаем так же: 36 млн переводов в СБП x 1/6 = 6 млн исходящих в СБП в сутки. Ещё 40 % переводов не выходят за пределы банка, поэтому всего исходящих 6 / 0,6 = 10 млн в сутки, или 10 / 15,4 = 0,65 на DAU. Входящих столько же: обмен с другими банками сбалансирован. Перед каждым исходящим переводом получатель определяется запросом в СБП, поэтому таких запросов тоже 0,65 на DAU.

Сессий на пользователя в сутки считаем по опросу [[8]](https://www.rshb.ru/news/05062026-000001). Ежедневно заходят в банковское приложение 65 % респондентов: 36 % - 1-2 раза в день, 18 % - 3-5 раз, 11 % - более пяти раз. DAU - это пользователи, зашедшие в приложение сегодня, поэтому нормируем доли на ежедневных пользователей: 36 / 65 = 0,55; 18 / 65 = 0,28; 11 / 65 = 0,17. Для интервалов берём середины (1,5 для "1-2" и 4 для "3-5"), для открытого интервала "более 5" принимаем 6. Получаем 0,55 x 1,5 + 0,28 x 4 + 0,17 x 6 = 3 сессии в сутки, всего 3 x 15,4 = 46,2 млн сессий в сутки.

За одну сессию пользователь выполняет один вход и один запрос баланса: по продуктовому решению баланс считает только сервер, поэтому он запрашивается при каждом открытии приложения. Там же загружается первая страница ленты операций - один запрос на сессию; дозагрузка отдельно не учитывается из-за отсутствия данных. График платежей заёмщик смотрит раз в месяц перед платежом: 7,1 млн кредитов / 30 = 236 тыс. запросов в сутки, или 0,015 на DAU. Поиск по истории принимаем равным одному разу в неделю на DAU (1/7 = 0,14 в сутки) - это допущение, статистики по нему нет.

Операции по вкладам и кредитам считаются от числа продуктов. Число открытий и выдач получается из размера портфеля, среднего срока и темпа роста базы (8,9 % в год, п. 2.1): в год закрывается портфель / срок, а открывается столько же плюс прирост.

- закрытие вклада: 5,8 млн вкладов при среднем сроке 6 месяцев → 5,8 / 0,5 = 11,7 млн в год, или 32 тыс. в сутки. Пролонгации в MVP нет, поэтому окончание срока считается закрытием, а продление - новым открытием;
- открытие вклада: закрытия плюс прирост 8,9 % x 5,8 млн = 0,5 млн в год → 12,2 млн в год, или 33 тыс. в сутки;
- пополнение вклада: одно в месяц на вклад → 5,8 млн / 30 = 194 тыс. в сутки. Это допущение: статистики по частоте пополнений нет, частота привязана к зарплатному циклу;
- выдача кредита: 7,1 млн кредитов при среднем сроке 3 года → погашается 2,4 млн в год, с приростом 8,9 % выдаётся 3,0 млн в год, или 8,2 тыс. в сутки;
- заявка на кредит: одобряется 25 % заявок → 8,2 / 0,25 = 33 тыс. в сутки; скоринг выполняется по каждой заявке.

Фоновые операции MVP на DAU не делятся и считаются отдельно:

- начисление процентов: по каждому вкладу и кредиту раз в сутки, 5,8 + 7,1 = 12,9 млн проводок в ночное окно 03:00-05:00 МСК;
- списание по графику: 7,1 млн кредитов / 30 дней = 236 тыс. в сутки, в том же ночном окне.

Push-уведомление отправляется по каждой клиентской финансовой операции (платёж, перевод, операция по вкладу, выдача кредита, списание по графику) и по решению по кредитной заявке. Ежесуточное начисление процентов уведомлений не порождает.

Влияние на продуктовые метрики:
- Около 80 % пользователей (европейская часть и Урал) получают RTT до своего ДЦ не больше 25 мс.
- Дальний Восток (5 % населения) получает 80-100 мс. Пользователь этого не заметит, поскольку время ответа определяется обработкой операции и обменом с НСПК.
- Отказ любого одного ДЦ не останавливает банк (п. 3.3).

Почему три ДЦ:
- Один ДЦ исключён. Физических отделений нет, и отказ единственного ДЦ означает полную недоступность банка
- При двух ДЦ каждый должен уметь держать 100 % нагрузки, то есть запас x2. Кроме того, из двух площадок нельзя собрать кворум для синхронной репликации.
- При трёх ДЦ каждый рассчитан на 53 % нагрузки на случай отказа соседнего (запас около x1,5). Кворум "2 из 3" переживает потерю одного ДЦ, и каждая из _трёх_ реплик (п. 2.3.1) хранится в своём ДЦ.
- Больше трёх ДЦ не нужно. Кворум из N ДЦ переживает ⌊(N−1)/2⌋ отказов, поэтому чётное число ДЦ не добавляет отказоустойчивости. Например, 4 ДЦ, как и 3, переживают один отказ, при этом каналов между ДЦ становится вдвое больше (6 vs 3). 4 ДЦ экономят лишь 17 % мощностей (133 % против 150 %). 5 ДЦ переживают два отказа, но требуют 167 % мощностей, то есть дороже трёх. Защита от одновременного отказа двух ДЦ не окупается: ДЦ стоят в разных городах с независимым электропитанием и каналами связи, поэтому одновременный отказ двух из них крайне маловероятен.

### 3.5. Anycast-балансировка

| Подсеть | Тип | Где анонсируется | Что на ней |
| --- | --- | --- | --- |
| 203.0.113.0/24 | anycast | все три ДЦ | авторитативный DNS ns1, ns2 |
| 198.51.100.0/24 | unicast | ДЦ-1 Москва | api-msk, API для регионов ДЦ-1 |
| 192.0.2.0/24 | unicast | ДЦ-2 Санкт-Петербург | api-spb, API для регионов ДЦ-2 |
| 198.18.0.0/24 | unicast | ДЦ-3 Екатеринбург | api-ekb, API для регионов ДЦ-3 |

Адреса условные. Anycast-подсеть анонсируется по BGP из всех ДЦ, и провайдер доставляет DNS-запрос в ближайший. При отказе DNS в ДЦ анонс снимается, запросы быстро уходят в соседние ДЦ.

Клиентский API на anycast не переводится по трём причинам:
- Распределением при anycast управляет маршрутизация провайдеров, а не банк. Москву и МО (15 % населения в одной точке) нельзя поделить между ДЦ, и ДЦ-1 получил бы перекос.
- Смена BGP-маршрута рвёт TCP-соединение, в том числе посреди платежа.
- Главный плюс anycast, быстрое переключение, даёт само приложение (п. 3.6).

### 3.6. Регулировка трафика между ДЦ

- При штатном режиме работы перераспределение идёт через веса GeoDNS. Можно сдвинуть долю Москвы между ДЦ-1 и ДЦ-2 или перенести регион в другой ДЦ.
- При отказе ДЦ DNS по health-check убирает его из ответов. Приложение при ошибке соединения или таймауте сразу повторяет запрос на резервный адрес (api-msk / api-spb / api-ekb по таблице отказов), не дожидаясь истечения TTL. Повтор платежа безопасен благодаря "ключу идемпотентности".
- При плановых работах вес ДЦ снижается до 0. ДЦ отключается, когда трафик падает почти до нуля. Клиентов, у которых ответ DNS закэширован дольше TTL, переключает уже приложение.

### 4.1. Схема балансировки


ДЦ делится на две зоны: группы стоек с независимым питанием и своими парами leaf-коммутаторов. Зоны служат доменами отказа при размещении ingress-узлов и подов.

| Уровень | Технология | Назначение | На ДЦ | Резервирование |
| --- | --- | --- | --- | --- |
| Выбор ДЦ | GeoDNS (раздел 3) | приводит клиента на VIP ДЦ | - | N+1 по ДЦ: 3 ДЦ по 53 % |
| Вход в ДЦ | пограничные маршрутизаторы, 2 оператора связи | BGP с операторами | 2 | 2N |
| Маршрутизация (L3/L4) | spine-leaf фабрика, ECMP с resilient hashing | раскидывает TCP-соединения по ingress-узлам по хешу 5-tuple | 2 spine, 2 leaf на стойку | 2N |
| L7 и терминация TLS | NGINX Ingress Controller на выделенных узлах | TLS, авторизация, лимиты, маршрутизация по URL, выбор пода на каждый запрос | 4 | 2(N+1), N = 1 (п. 4.3) |
| Межсервисный L7 | Envoy-sidecar, Istio | mTLS, выбор экземпляра на каждый запрос, таймауты, повторы | в каждом поде | не требуется |
| Сервисы | поды Kubernetes | бизнес-логика, stateless | - | 2N по зонам |
| Межбанковский вход | выделенные каналы, криптошлюзы, шлюз обмена | постоянные соединения с НСПК и СБП | 2 + 2 в ДЦ-1 и ДЦ-2 | 2N и второй ДЦ |
| Выход в интернет | egress-шлюз Envoy | push в APNs/FCM, запросы в БКИ | 2 | 2N |
| СУБД | пулер соединений | мультиплексирует соединения сервисов к СУБД | 2 | 2N |

Выбранные схемы:
- **Входящие запросы:** ECMP → ingress NGINX → под сервиса. Ingress-узлы анонсируют VIP ДЦ по BGP (MetalLB), анонс есть только у узла, где ingress прошёл readiness-пробу. Под выбирается алгоритмом `random two least_conn`. POST повторяется на другом поде только при наличии ключа идемпотентности (п. 3.6).
- **Отдельного уровня L4 (LVS) нет.** Его роль выполняет ECMP фабрики: весь пик ДЦ обрабатывает один ingress-узел (п. 4.3), а роутингом можно балансировать на надёжные выделенные узлы. L4 с таблицей соединений (Maglev, DPVS) понадобится, если ingress-узлов станут десятки.
- **Межсервисные запросы:** Envoy-sidecar в каждом поде, список подов рассылает istiod по результатам readiness-проб. Экземпляр выбирается по least request (power of two choices): сначала своя зона, затем свой ДЦ, затем соседний. ClusterIP (kube-proxy) не подходит: он балансирует соединения, а HTTP/2 и gRPC держат одно соединение, и все запросы пода уходят в один под.
- **Межбанковские запросы:** соединения по выделенным каналам постоянные, сообщения между ними распределяет сама платёжная система. Шлюз обмена передаёт сообщение в ДЦ клиента через сервисную сеть.

### 4.2. Терминация TLS

- Внешний TLS терминируется на ingress-узлах, внутри ДЦ работает mTLS сервисной сети.
- Один VIP на ДЦ, внутри ДЦ ECMP, session tickets с общим ключом на ingress-узлах всех трёх ДЦ. Клиент возобновляет сессию без полного handshake на любом узле, в том числе после переключения ДЦ. Ключ меняется раз в сутки.
- TLS 1.3, для старых устройств TLS 1.2 с ECDHE. 0-RTT выключен: повтор раннего запроса мог бы провести платёж дважды.
- Сертификат ECDSA P-256 с запасным RSA-2048, в приложении certificate pinning.

Основное значение взято из самого свежего измерения [[18]](https://www.haproxy.com/blog/state-of-ssl-stacks): текущие версии OpenSSL 3.x, 664 handshakes/с на ядро. Стоимость handshake определяется TLS-библиотекой, а nginx использует ту же OpenSSL, поэтому оценка к нему применима. По [[18]](https://www.haproxy.com/blog/state-of-ssl-stacks) OpenSSL 3.x отстаёт от 1.1.1 в основном из-за блокировок между потоками. Рабочие процессы nginx однопоточные, так что для nginx эта оценка скорее пессимистична.

- на handshakes: C_TLS = 2 969 / 664 = 4,5 ядра;
- на запросы в установленных соединениях: по [[17]](https://blog.nginx.org/blog/testing-performance-nginx-ingress-controller-kubernetes) 28 640 HTTPS-запросов/с на ядро при ответе 1 КБ, для ответа 10 КБ (страница ленты) по [[16]](https://blog.nginx.org/blog/testing-the-performance-of-nginx-and-nginx-plus-web-servers) в 0,58 раза меньше, 16 600 запросов/с. C_RPS = 2 969 / 16 600 = 0,18 ядра;
- запас 1,5 на журнал запросов, подзапросы авторизации и агенты узла, выключенные в бенчмарках: C = (4,5 + 0,18) x 1,5 ≈ 7 ядер.

Проверка на самой медленной библиотеке, OpenSSL 3.0 (328 на ядро): C = (2 969 / 328 + 0,18) x 1,5 ≈ 14 ядер. Это тоже укладывается в один узел.

**Ограничитель 2: сеть.** По [[17]](https://blog.nginx.org/blog/testing-performance-nginx-ingress-controller-kubernetes) ingress-контроллер пропускает 8,8 Гбит/с, упираясь в карту 10 GbE:

N_net = ⌈0,10 / 8,8⌉ = 1, загрузка 1,2 %

**Итог.** Узел: 16 физических ядер, 64 ГБ ОЗУ, 2 x 25 GbE. По [[16]](https://blog.nginx.org/blog/testing-the-performance-of-nginx-and-nginx-plus-web-servers) и [[17]](https://blog.nginx.org/blog/testing-performance-nginx-ingress-controller-kubernetes) до 16 ядер производительность растёт почти линейно. По [[18]](https://www.haproxy.com/blog/state-of-ssl-stacks) до 12-16 потоков все библиотеки идут вровень, расхождение начинается дальше.

N = max(⌈7 / 16⌉, ⌈0,10 / 8,8⌉) = 1

Весь пик ДЦ обрабатывает один узел, поэтому число узлов определяет надёжность:
- N+1 внутри зоны: один узел может быть на обновлении или в отказе;
- x2 по зонам: каждая зона в одиночку держит всю нагрузку ДЦ.

**Итого 2(N+1) = 4 ingress-узла на ДЦ, 12 на три ДЦ.** Схема 2N с двумя узлами оставляла бы ДЦ без резерва на время обновления узла.

| Состояние | Узлов в работе | Загрузка CPU узла в худшем режиме |
| --- | --- | --- |
| Штатно | 4 | 11 % |
| Отказ зоны | 2 | 22 % |
| Отказ зоны и узла в оставшейся зоне | 1 | 44 % |

### 4.4. Отказоустойчивость

| Отказ | Что происходит |
| --- | --- |
| Ingress-узел | BFD обнаруживает отказ за доли секунды, анонс VIP снимается, ECMP переводит соединения узла на остальные. Клиенты возобновляют TLS-сессию по тикету и повторяют запрос с тем же ключом идемпотентности |
| Зона ДЦ | трафик принимают ingress-узлы и поды второй зоны, их хватает на всю нагрузку (2N) |
| Маршрутизатор или оператор связи | трафик идёт через второй маршрутизатор и второго оператора |
| Под сервиса или его перегрузка | readiness-проба, пассивная проверка nginx и outlier detection Envoy убирают под из балансировки. Идемпотентный запрос повторяется на другом поде по таймауту, выбранному по квантилям |
| Все поды сервиса в ДЦ | Envoy отправляет запросы в соседний ДЦ через east-west-шлюз |
| ДЦ целиком | п. 3.6 |

| SESSION | строгая внутри ДЦ, между ДЦ не реплицируется | token_hash, равномерно; чтение на каждом запросе API |
| OTP_CODE | атомарный счётчик попыток | phone; нагрузка мала |
| IDEMPOTENCY_KEY | строгая, в одной транзакции с создаваемой записью | (client_id, key), равномерно |
| RECIPIENT_LOOKUP | read-after-write | id, равномерно |
| EVENT | доставка не реже одного раза, порядок внутри клиента | client_id - события клиента идут по порядку |
| OPERATION_SEARCH | в конечном счёте, отставание до секунд | client_id - поиск затрагивает данные одного клиента |

- имя контрагента, MCC и категория в operations - снимок на момент операции (п. 5), а не копия.

### 6.4. Индексы

Под каждый запрос к операциям - свой индекс. Ключ шардирования всех шардированных коллекций - client_id (п. 6.6). Каждый запрос от клиента содержит client_id, поэтому mongos отправляет его в один шард, и там работает индекс, начинающийся с client_id. Индексы, которые начинаются не с client_id, используют только:
- обязательный индекс _id: он есть в каждой коллекции MongoDB, а поиск операции всегда идёт вместе с client_id;
- частичные индексы ночных задач (status, _id): задача запускается на каждом шарде и обходит только его данные.

| Коллекция | Ключ шардирования | Индекс ключа шардирования |
| --- | --- | --- |
| operations_ГГГГММ | client_id | (client_id, _id ↓) |
| accruals | client_id | (client_id, product_id, month), уникальный |
| accounts, cards, deposits, loans | client_id | (client_id, _id) |
| idempotency_keys | client_id | (client_id, key), уникальный |
| clients, devices, client_documents, card_by_pan, loan_applications, loan_schedule, справочники | нет, коллекции на шарде mongo-global | - |

Размер = записей x байт на запись / заполнение страницы. Индекс WiredTiger - B-дерево:
- запись = ключ в формате KeyString (int64 и дата - около 9 Б, int32 - около 3 Б, строка - длина + 2 Б, binData - длина + 3 Б) + RecordId 8 Б + 2 Б служебных;
- префиксное сжатие индексов включено по умолчанию: общий с соседней записью префикс хранится один раз. В индексах, начинающихся с client_id, соседние записи почти всегда одного клиента, поэтому эти 9 Б не повторяются;
- заполнение страниц - 90 %, если ключ растёт (_id, дата), и около 70 %, если вставка идёт в случайное место.

| FILE_OBJECT (фото документов) | S3 на Ceph RGW в своих ДЦ | 82 ТБ неизменяемых объектов по 500 КБ, 2,5 записи в секунду; отдельный кластер ради защиты персональных данных, другие системы его не нагружают |
| Отчёты БКИ | MongoDB, внутри документа заявки | 60 млн файлов по 10 КБ - для объектного хранилища это проблема мелких файлов |

Почему не другие СУБД для основных данных:
- PostgreSQL - шардирование, маршрутизацию и перенос данных между шардами пришлось бы делать вручную, а переводы между шардами - сагой;
- YDB - нет восстановления на момент времени, а платёж затрагивает несколько таблиц и становится распределённой транзакцией (20-500 мс);
- Cassandra, ScyllaDB - нет транзакций между партициями: остаток и операцию нельзя изменить атомарно;
- CockroachDB - с 2024 года нет open source версии, нужна платная лицензия зарубежного вендора;
- Tarantool - данные в памяти, 46 ТБ в RAM нереально; vshard не выполняет транзакции между шардами.

Риск MongoDB: вендор с 2022 года не продаёт ПО в России. Используется открытая версия, эксплуатация своими силами.

### 6.6. Шардирование и резервирование

**Ключ шардирования всех шардированных коллекций - client_id, по диапазонам.**
- Почему client_id: почти все запросы адресованы одному клиенту (п. 5.4), а клиентов 54,9 млн, поэтому данные и нагрузка распределяются равномерно. Все документы одной денежной транзакции (счёт, операция, ключ идемпотентности) относятся к одному клиенту и лежат на одном шарде.
- Почему по диапазонам, а не по хешу: нужны зоны. Зона закрепляет диапазон client_id за шардом. Так все коллекции клиента оказываются на одном шарде, а клиент - в ДЦ своего региона. Зоны задаются только диапазонами ключа.
- Как устроен client_id: client_id = группа x 2^53 + время регистрации и счётчик. Группа - старшие 10 бит, 1 024 значения. Все client_id одной группы образуют непрерывный диапазон, поэтому группу можно целиком закрепить за шардом.

**Зоны.** Каждому шарду назначена зона из 16 соседних групп, то есть один непрерывный диапазон client_id: шард 1 - группы 0-15, шард 2 - группы 16-31 и т. д. Зоны одинаковы для всех 7 шардированных коллекций. При регистрации клиент получает группу из шардов, primary которых в ДЦ его региона: ДЦ-1 - 23 шарда, ДЦ-2 - 21, ДЦ-3 - 20, пропорционально нагрузке (п. 3.3). Внутри ДЦ выбирается наименее заполненная группа, поэтому шарды заполняются равномерно. Перешардирование - новый шард и перенос части групп в его зону: балансировщик сам перевозит данные, client_id не меняются.

### 6.8. Балансировка запросов и мультиплексирование подключений

**MongoDB:** под (пул драйвера) → роутеры mongos на узлах-пулерах (2 на ДЦ, п. 4.1) → primary или вторичный член нужного шарда.
- Драйвер получает список mongos и выбирает ближайшие по задержке, то есть роутеры своего ДЦ. При отказе роутера запросы уходят на соседний.
- mongos по client_id из запроса и зонам направляет запрос в один шард. Тысячи соединений от подов он сводит к пулам соединений к каждому шарду.
- Денежные запросы читают и пишут только в primary. Маршрутные чтения из mongo-global (card_by_pan, clients по phone, push-токены) идут на ближайший член.
- После выборов нового primary драйвер и mongos сами переключаются на него, сервисы ничего не перенастраивают.
- Запрос клиента выполняется в ДЦ, где primary его шарда. Клиентский API попадает туда по GeoDNS, потому что группа client_id выбрана по региону. Межбанковские сообщения передаются туда из ДЦ-1 и ДЦ-2 по межДЦ-каналам (п. 3.3).

**Redis:** go-redis держит пул соединений к мастеру своего ДЦ, адрес мастера узнаёт у Sentinel. Прокси не нужен: около 6 тыс. операций в секунду.

**Kafka:** продюсеры и потребители ходят напрямую к лидерам партиций. Нагрузку распределяет размещение 64 партиций по брокерам и между потребителями группы.

**OpenSearch:** клиент по кругу обращается к координирующим узлам своего ДЦ. Поиск с routing = client_id попадает в один шард каждого годового индекса.

**S3:** узлы Ceph RGW не хранят состояния, запросы между ними распределяет ingress NGINX (п. 4).

### 6.9. Схема резервного копирования

| Эшелон | Как сделано | От чего защищает | Потеря данных | Время восстановления |
| --- | --- | --- | --- | --- |
| Горячий резерв | члены replica set в двух других ДЦ, запись с writeConcern majority | отказ узла или ДЦ | 0 | ~10-15 с |
| Отложенный член | скрытый член в каждом replica set, secondaryDelaySecs = 4 ч | ошибочное изменение или удаление, замеченное в течение 4 ч | 0 | минуты: документы берутся с отложенного члена |
| Бэкап + oplog | Percona Backup for MongoDB со вторичных членов: полный физический бэкап раз в месяц, инкрементальный раз в сутки, oplog непрерывно; хранение 35 сут | ошибка, замеченная в течение месяца | восстановление на любую секунду | около часа: шарды восстанавливаются параллельно, 0,72 ТБ на шард |

| Redis | не бэкапится: TTL не больше 15 мин, потеря означает повторный вход или повтор действия | - |
| Kafka | не бэкапится: RF 3, источник данных - MongoDB | - |
| OpenSearch | инкрементальный снапшот в S3 раз в сутки, хранится 7 снапшотов | ~30 ТБ первый, дальше только новые сегменты |
| S3, фото | версионирование: удалённые и перезаписанные версии хранятся 35 сут; копия в ДЦ-2 | - |

Пример восстановления: ошибочно удалили операции у 1 % клиентов и заметили через месяц.
1. Кластер восстанавливается из бэкапа на отдельные серверы на момент перед ошибкой: полный бэкап, инкременты и oplog до нужной секунды. Шарды восстанавливаются параллельно, около часа.
2. По client_id находим документы этих клиентов в восстановленном кластере.
3. Вставляем их обратно в рабочий кластер, остатки сверяем с операциями.

Если ошибку заметили позже 35 сут, операции берутся из архива закрытых месяцев.

## 7. Алгоритмы

В разделе описаны два алгоритма денежного ядра, от которых зависят схема хранения, профиль нагрузки и взаимодействие сервисов:

- **7.1. Отложенное зачисление на горячий счёт.** Снимает неоднозначность из п. 5.4: «горячий счёт - получатель массовых переводов, все зачисления в одну строку».
- **7.2. Согласованная видимость межшардового перевода без глобальных часов.** Уточняет, как работает распределённая транзакция из п. 6.6, на которую опираются переводы между шардами.

Алгоритмы связаны. Длительность межшардовой транзакции (п. 7.2) определяет, сколько зачислений в секунду выдерживает один счёт. Этот предел и обходит алгоритм п. 7.1.

Остальные функции MVP реализуются стандартными способами и в раздел не включены.

### 7.1. Отложенное зачисление на горячий счёт

**Наименование.** Адаптивное отложенное зачисление (buffered posting). Зачисления на горячий счёт записываются отдельными документами в буфер. Фоновый процесс периодически переносит их сумму в остаток одной транзакцией.

**Блок.** Сервис счетов, функция зачисления: входящий перевод внутри банка и из СБП, закрытие вклада, выдача кредита. Коллекции accounts и operations в mongo-core (п. 6).

#### 7.1.1. Постановка задачи

Горячий счёт - это счёт, на который одновременно приходит много зачислений: благотворительный сбор, донаты блогеру во время эфира, сбор денег на подарок. Каждое зачисление меняет один и тот же документ accounts (поле balance).

MongoDB выполняет транзакции с изоляцией snapshot isolation. Если две параллельные транзакции меняют один документ, одна из них прерывается с ошибкой WriteConflict [[21]](https://www.mongodb.com/company/blog/engineering/formal-methods-beyond-correctness-isolation-permissiveness-distributed-transactions) и повторяется клиентом. Очереди к документу нет. Поэтому документ пропускает не больше 1 / T_окна изменений в секунду, где T_окна - время от начала транзакции до её фиксации. Две транзакции, чьи окна пересеклись, обе успешно изменить документ не могут.

| Вид зачисления | Окно занятости документа счёта | Предел на один счёт |
| --- | --- | --- |
| Транзакция в одном шарде: входящий из СБП, закрытие вклада, выдача кредита, перевод внутри шарда | 3-5 мс (3 команды внутри ДЦ) | 200-300 в секунду |
| Перевод из другого шарда, primary обоих шардов в одном ДЦ | 30-70 мс (3 записи majority по 9-23 мс, п. 7.2) | 15-30 в секунду |
| Перевод из другого шарда, primary в разных ДЦ (около 2/3 межшардовых переводов, п. 7.2.2) | 100-140 мс (п. 7.2.7) | 7-10 в секунду |

Пример: сбор, на который приходит 200 переводов в секунду. Это в 7-30 раз выше предела межшардового зачисления. Неудачные попытки повторяются, число одновременных повторов растёт, повторы и ожидания занимают тикеты записи шарда. В итоге деградирует весь шард [[22]](https://jira.mongodb.org/browse/SERVER-126462), а на нём около 858 тыс. клиентов (54,9 млн / 64).

Задача: принимать на один счёт до тысяч зачислений в секунду так, чтобы каждое было учтено ровно один раз. При этом нельзя ослабить проверку остатка при списании и нельзя замедлить обычные счета.

#### 7.1.2. Исходные данные, ограничения и требования

| | Содержание |
| --- | --- |
| Входные данные | Поток зачислений: account_id, amount, operation_id. У обычного счёта зачисления редки: 10 млн входящих переводов в сутки на 91 млн счетов. Какой счёт станет горячим, заранее неизвестно |
| Ограничения | MongoDB 8.0: snapshot isolation, при конфликте WriteConflict без ожидания (п. 6.5). Зачисление атомарно с записью операции в ленту, проверка остатка при списании строгая (п. 5.4). Новых систем в денежном контуре нет |
| Требования к результату | Каждое зачисление учтено ровно один раз. Операция видна в ленте и приходит push сразу после фиксации. Деньги доступны для списания не позже чем через 2 с. Документ горячего счёта меняется не чаще 5 раз в секунду, это ниже любого предела из табл. 7.1.1. Путь обычных счетов не меняется |

#### 7.1.3. Последовательность работы

**Идея.** Зачисление и списание несимметричны:
- зачисление только увеличивает остаток и не может увести его в минус, поэтому перенос суммы в остаток можно отложить;
- списание откладывать нельзя: проверка «хватает ли денег» должна видеть актуальный остаток.

Зачисления на горячий счёт превращаются из изменений одного документа во вставки разных документов, а вставки разных документов друг с другом не конфликтуют.

Инвариант, который сохраняет каждый шаг: для любого счёта `balance + Σ pending_credits(счёт) = сумма всех проведённых по нему операций`. Флаг режима в инварианте не участвует.

```mermaid
flowchart LR
  TX["Транзакция зачисления"] --> MODE{"credit_mode счёта"}
  MODE -->|direct| DIR["balance += amount"]
  MODE -->|buffered| BUF["вставка в pending_credits"]
  BUF --> FOLD["Обработчик свёртки шарда, раз в 200 мс: записи старше 1 с"]
  FOLD --> FTX["Транзакция: удалить записи, balance += их сумма"]
  TX -.->|2 WriteConflict подряд| ON["credit_mode = buffered"]
  FOLD -.->|меньше 1 зачисления в секунду 10 мин| OFF["credit_mode = direct"]
```

**Шаг 1. Зачисление.** Выполняется внутри денежной транзакции из п. 6.3.
1. Прочитать документ счёта: статус и credit_mode. Чтение с записями не конфликтует.
2. Вставить операцию в operations, как сейчас.
3. Если режим direct, увеличить balance. Если buffered, вставить в pending_credits документ {_id: Snowflake, account_id, operation_id, amount}; документ счёта при этом не меняется.
4. Зафиксировать транзакцию. Операция сразу видна в ленте, change stream запускает push (п. 6.7).

**Шаг 2. Включение режима.** Если зачисление на счёт прошло только с третьей попытки (два WriteConflict подряд), сервис записывает credit_mode = buffered одиночной командой вне транзакции. Ложное срабатывание безвредно: например, конфликт мог случиться на стороне отправителя. Режим buffered корректен для любого счёта.

**Шаг 3. Свёртка.** На каждый шард работает один обработчик, цикл раз в 200 мс:
1. Вычислить водяной знак W = now − 1 с. По обязательному индексу _id выбрать записи pending_credits своего шарда, у которых _id < W. Обработчик работает на каждом шарде и обходит только его данные, как ночные задачи (п. 6.4).
2. Для каждого счёта выполнить одну транзакцию: удалить до 1 000 его записей и увеличить balance на их сумму. Если записей больше, сделать несколько транзакций подряд.
3. Не запоминать позицию «обработано до такого-то _id». Каждый цикл сканирует буфер от начала, а свёрнутые записи из него уже удалены. Если запись получила _id раньше, а зафиксировалась позже (долгая 2PC, п. 7.2), она будет свёрнута в следующем цикле. С сохранённой позицией она была бы пропущена навсегда.

**Шаг 4. Выключение режима.** Если 10 минут подряд на счёт приходит меньше одного зачисления в секунду, обработчик записывает credit_mode = direct. Записи, которые остались в буфере или пришли от транзакций, начатых до переключения, всё равно сворачиваются: обработчик ищет их по самому буферу, а не по флагу.

**Шаг 5. Чтение баланса и списание.**
- **Показываемый остаток** равен balance + Σ pending_credits счёта и читается в одной read-only транзакции с readConcern snapshot. Если читать двумя отдельными запросами, свёртка между ними посчитает деньги дважды или потеряет их.
- **Доступно для списания** = balance − hold_amount, без буфера, то есть консервативно.
- **Если денег не хватает, а буфер не пуст,** списание сначала синхронно сворачивает буфер этого счёта и затем проверяет остаток заново.
- **Закрытие счёта** начинается со свёртки буфера.

**Корректность при сбоях:**
- Удаление записей буфера и увеличение balance выполняются в одной транзакции. Сбой обработчика откатывает их вместе.
- Два обработчика на одном шарде не задвоят сумму: вторая транзакция попытается удалить уже удалённые записи, получит WriteConflict и повторит выборку. Один обработчик на шард нужен ради экономии, а не ради корректности.

#### 7.1.4. Структуры данных

| Структура | Где | Содержание |
| --- | --- | --- |
| Коллекция pending_credits (новая) | mongo-core, ключ шардирования client_id по диапазонам, те же зоны, что у accounts (п. 6.6) | _id int64 (Snowflake, время создания); client_id int64; account_id int64; operation_id int64; amount int64. Документ BSON 95 Б |
| Индексы pending_credits | | _id - выборка обработчиком по водяному знаку; (client_id, _id) - индекс ключа шардирования, баланс и свёртка счёта |
| Поля accounts | mongo-core | credit_mode int32 (direct / buffered), hot_since date. Хранятся только у счетов, которые были горячими; отсутствие поля означает direct |
| Счётчики обработчика | память обработчика | число свёрнутых записей по счёту за минуту, окно 10 мин - для выключения режима |

В буфере одновременно находится поток × 1,3 с записей: при 200 зачислениях в секунду около 260 документов (25 КБ), при 5 000 в секунду около 6 500 документов (0,6 МБ).

#### 7.1.5. Альтернативные решения

| Вариант | Предел на один счёт | Когда деньги доступны для списания | Недостатки |
| --- | --- | --- | --- |
| Прямое изменение остатка с повторами при конфликте (как в п. 6) | 7-300 в секунду (табл. 7.1.1) | сразу | при превышении предела - лавина повторов, деградирует весь шард |
| Изменять остаток отдельной командой вне транзакции (одиночные записи MongoDB повторяет сама) | выше, ограничен шардом | сразу | нарушает атомарность операции и остатка (п. 5.4): сбой между командами оставит операцию без денег, нужна сверка. Межшардовый перевод так не сделать |
| Очередь на счёт: зачисления в партицию Kafka по account_id, один потребитель применяет их пачками | тысячи в секунду | 0,1-2 с | Kafka в денежном контуре; гарантия «ровно один раз» у потребителя; списания должны идти через ту же очередь. Uber отказался от такой схемы из-за задержки потребителя в 1-2 с [[19]](https://www.uber.com/en-LK/blog/high-throughput-processing/) |
| Разбить остаток на N субсчетов, зачисление - в случайный субсчёт | N × предел | сразу | N задаётся заранее; списание ищет субсчёт с достаточной суммой, а если ни в одном не хватает, затрагивает несколько субсчетов и снова конфликтует; баланс - сумма N документов |
| Специализированная учётная БД (TigerBeetle) | очень высокий: пачки до 8 тыс. переводов, одна репликация на пачку [[31]](https://docs.tigerbeetle.com/concepts/performance/) | сразу | замена денежного ядра и второй источник правды об остатке, технология без поддержки в РФ |
| Ограничить частоту зачислений на счёт | предел первого варианта | - | клиентам отказывают в переводе, деньги не доходят |
| **Отложенное зачисление (выбрано)** | **тысячи в секунду: вставки разных документов не конфликтуют** | **через 1,2-1,3 с, в ленте и push - сразу** | новая небольшая коллекция и фоновый обработчик |

Отложенное зачисление на горячие счета применяется в промышленных платёжных системах. Например, Modern Treasury рекомендует писать записи на горячий счёт асинхронно и применять их пачками [[20]](https://docs.moderntreasury.com/docs/handling-concurrency).

#### 7.1.6. Обоснование выбора и параметров

**Почему выбрано отложенное зачисление:**
- Использует несимметричность: откладываются только зачисления, а списания проверяют остаток так же строго, как раньше.
- Работает только на счетах, где возникли конфликты. Путь обычных счетов не меняется.
- Использует только MongoDB, без новых систем в денежном контуре.
- Корректность не зависит ни от флага режима, ни от единственности обработчика: инвариант сохраняет каждая транзакция.

| Параметр | Значение | Обоснование |
| --- | --- | --- |
| Период свёртки | 200 мс | документ счёта меняется не чаще 5 раз в секунду, это ниже предела межДЦ-зачисления 7-10 в секунду |
| Водяной знак | now − 1 с | в 7-8 раз больше межшардовой транзакции (около 130 мс, п. 7.2.7). Обработчик почти не попадает на подготовленные записи и не ждёт их (п. 7.2.3); корректность от водяного знака не зависит |
| Пачка | до 1 000 записей на транзакцию | при 5 циклах в секунду одна транзакция на цикл покрывает 5 000 зачислений в секунду, больший поток сворачивается несколькими транзакциями |
| Включение | 2 WriteConflict подряд при зачислении | у обычного счёта два конфликта подряд почти невозможны, а ложное включение безвредно |
| Выключение | меньше 1 зачисления в секунду 10 мин | гистерезис: счёт не переключается туда-обратно во время эфира с паузами |

#### 7.1.7. Влияние на физическую схему, нагрузку и взаимодействие

- **Физическая схема (п. 6):**
  - новая коллекция pending_credits в mongo-core, размер меньше 1 МБ;
  - два поля в accounts, только у бывших горячих счетов;
  - у pending_credits только обязательный индекс _id и индекс ключа шардирования (client_id, _id), новых типов индексов нет;
  - чтение баланса выполняется read-only транзакцией snapshot.
- **Нагрузка:**
  - Обычные счета: без изменений.
  - Горячий счёт с 200 зачислениями в секунду: шард получает +200 вставок в буфер и +200 удалений при свёртке, а также 5 обновлений accounts в секунду. Это около +400 записей в секунду к 119 записям в секунду пика шарда (п. 6.6). Без алгоритма тот же поток дал бы лавину повторов.
  - Сворачиватель: 64 обработчика, по одному циклу раз в 200 мс; на шарде без горячих счетов цикл - один пустой запрос по индексу.
- **Взаимодействие:**
  - Новый компонент - обработчик свёртки. 64 экземпляра, каждый в ДЦ primary своего шарда; единственность обеспечивает аренда (lease) в mongo-global.
  - Лента, push и поиск не меняются: операция записывается сразу.
  - Мониторинг: доля WriteConflict по счёту, размер буфера, отставание свёртки.

### 7.2. Согласованная видимость межшардового перевода без глобальных часов

**Наименование.** Двухфазная фиксация (2PC) MongoDB с гибридными логическими часами (HLC). Метка фиксации транзакции - максимум меток подготовки участников. Читатель, который попал на подготовленную запись и чья метка чтения не меньше метки подготовки, ждёт решения.

**Блок.** Сервис переводов: перевод внутри банка, когда отправитель и получатель лежат на разных шардах. Это 63 из 64 внутренних переводов, до 137 в секунду в пике (п. 6.6). Механизм встроен в MongoDB. Проектные решения: выбор механизма вместо альтернатив, порядок команд, параметры и токен согласованности в API.

#### 7.2.1. Постановка задачи

Шард - отдельный replica set со своими часами. Перевод Ани (шард 7) Боре (шард 42) меняет оба шарда. Требуется:

1. **Атомарность:** обе части фиксируются или ни одна.
2. **Атомарная видимость:** любой читатель (клиент, сверка, change stream для push и поиска) видит либо обе части, либо ни одной. Состояние «у Ани списано, Боре не зачислено» не должно быть видно ни в какой момент.
3. **Причинный порядок:** чтение, которое по цепочке сообщений следует за завершением перевода, видит перевод.
4. **Отказоустойчивость:** отказ любого узла или ДЦ не приводит ни к потере, ни к задвоению денег.

Для пункта 2 нужен один момент совершения перевода, общий для обоих шардов. Общих часов у шардов нет. Системное время узлов синхронизируется по NTP с погрешностью от единиц до десятков миллисекунд, а это сравнимо с RTT между ДЦ (9-23 мс). Поэтому упорядочивать события разных шардов по системным часам нельзя (п. 7.2.5).

#### 7.2.2. Исходные данные, ограничения и требования

| | Содержание |
| --- | --- |
| Входные данные | 64 шарда, primary шарда в ДЦ региона: ДЦ-1 - 23, ДЦ-2 - 21, ДЦ-3 - 20 (п. 6.6). RTT: Москва - Санкт-Петербург 9 мс, Москва - Екатеринбург 23 мс. Запись majority ждёт ближайший другой ДЦ: 9 мс для primary в ДЦ-1 и ДЦ-2, 23 мс для ДЦ-3. Межшардовых переводов до 137 в секунду. Доля переводов между шардами с primary в разных ДЦ: 1 − (23² + 21² + 20²) / 64² = 0,67, это оценка сверху, так как свои чаще переводят своим |
| Ограничения | Нет центрального узла времени: он стал бы единой точкой отказа и добавил бы обмен через межДЦ-канал на каждую транзакцию. Нет специального оборудования (GPS, атомных часов). MongoDB Community |
| Требования | Перевод фиксируется не дольше 300 мс. Половина перевода не видна ни одному читателю. Отказ ДЦ не теряет и не задваивает перевод. Документы счетов заняты как можно меньше времени |

#### 7.2.3. Последовательность работы

**Часы кластера.** Каждый узел ведёт метку времени кластера: пару (секунды, счётчик) [[24]](https://dl.acm.org/doi/10.1145/3299869.3314049).
- Primary шарда присваивает каждой записи метку больше предыдущей: секунды не меньше системного времени, счётчик упорядочивает события внутри секунды.
- Каждое сообщение между драйвером, mongos и шардами несёт метку отправителя, подписанную HMAC. Получатель сдвигает свои часы до max(свои, полученные).
- Итог: если событие B следует за A по любой цепочке сообщений, метка B больше метки A.

**Перевод.** Пример: Аня на шарде 7 (primary в ДЦ-3), Боря на шарде 42 (primary в ДЦ-1).

```mermaid
sequenceDiagram
  participant S as Сервис переводов, ДЦ-3
  participant R as mongos, ДЦ-3
  participant A as Шард 7 - Аня, координатор
  participant B as Шард 42 - Боря
  S->>R: команды перевода, метка чтения назначает mongos
  R->>A: ключ идемпотентности, списание, операция Ани
  R->>B: операция Бори, зачисление
  S->>R: commit
  R->>A: передать фиксацию координатору
  A->>A: записать список участников, majority
  par подготовка
    A->>A: prepare, P7 = 100, majority
  and
    A->>B: prepare
    B-->>A: P42 = 105, majority
  end
  A->>A: C = max(100, 105) = 105, записать решение, majority
  A-->>R: перевод зафиксирован
  R-->>S: успех и operationTime
  A->>B: commit с меткой C = 105
  A->>A: commit с меткой C = 105
```

1. mongos назначает транзакции глобальную метку чтения [[21]](https://www.mongodb.com/company/blog/engineering/formal-methods-beyond-correctness-isolation-permissiveness-distributed-transactions).
2. Команды выполняются на шардах. Первой выполняется запись на шард отправителя (ключ идемпотентности, списание). Координатором 2PC становится первый шард-участник [[27]](https://jira.mongodb.org/browse/SERVER-41356), поэтому координатор оказывается в ДЦ клиента.
3. Сервис вызывает commit. mongos передаёт фиксацию шарду-координатору.
4. Координатор записывает список участников с writeConcern majority.
5. **Подготовка.** Каждый участник i:
   - берёт метку подготовки P_i, равную текущему времени своих часов;
   - помечает изменённые документы как подготовленные;
   - пишет запись prepare в oplog и ждёт majority;
   - отвечает координатору меткой P_i.
6. Координатор вычисляет C = max(P_i), записывает решение «commit, C» с majority и отвечает клиенту [[27]](https://jira.mongodb.org/browse/SERVER-64515).
7. Участники фиксируют изменения с меткой видимости C. Координатор удаляет свой документ.

Если хотя бы один участник не смог подготовиться, решение - abort. Транзакции, которые затронули один шард, и транзакции только на чтение фиксируются без 2PC.

**Правило чтения.** Читатель с меткой R на шарде i видит запись подготовленной транзакции так [[21]](https://www.mongodb.com/company/blog/engineering/formal-methods-beyond-correctness-isolation-permissiveness-distributed-transactions):

| Состояние записи | R < P_i | R ≥ P_i |
| --- | --- | --- |
| Подготовлена, решения нет | не видна, ответ сразу | ждать решения |
| Зафиксирована с меткой C | видна, если C ≤ R | видна, если C ≤ R |

**Почему C = max(P_i).**
- Шард i отвечает читателю с R < P_i «не видно» сразу. Этот ответ останется верным, только если C > R для всех таких R, то есть C ≥ P_i. Условие должно выполняться на каждом участнике, значит C ≥ max(P_i). Максимум - наименьшая допустимая метка, то есть самая близкая к реальному времени.
- После решения видимость на каждом шарде определяется одним и тем же условием C ≤ R. До решения ждёт любой читатель, для которого ответ ещё не определён. Значит, ни один читатель не увидит половину перевода.
- **Контрпример для C < max(P_i).** P_7 = 100, P_42 = 105, C = 100, читатель с R = 103. Шард 42 сразу отвечает «не видно» (103 < 105). Шард 7 дожидается решения и показывает списание (100 ≤ 103). Читатель видит половину перевода.

**Почему P_i - текущее время, а не произвольная метка.** Метка подготовки и фиксации не может быть меньше метки любого уже выполненного чтения [[26]](https://source.wiredtiger.com/11.3.1/timestamp_txn_api.html). Иначе задним числом изменится ответ, уже отданный читателю. Текущее время часов шарда не меньше меток всех обслуженных им запросов, потому что часы сдвигаются по правилу HLC.

**Отказы.**
- **Primary участника отказал после подготовки.** Запись prepare подтверждена majority, поэтому новый primary восстанавливает подготовленную транзакцию из oplog и держит документы до решения. Отменить подготовленную транзакцию сам участник не может.
- **Координатор отказал.** Список участников и решение записаны с majority. Новый primary шарда-координатора поднимает документы координаторов и продолжает с прерванного шага [[27]](https://jira.mongodb.org/browse/SERVER-38806). До записи решения координатор может отменить транзакцию по истечении transactionLifetimeLimitSeconds, после записи - только зафиксировать [[27]](https://jira.mongodb.org/browse/SERVER-37881).
- **Цена отказа** - документы заняты на время выборов, 10-15 с (п. 6.6).

**Причинная, а не внешняя согласованность.** MongoDB гарантирует, что перевод увидит запрос, который несёт метку не меньше C. Если Боря узнал о переводе вне системы (по телефону) и его запрос попал на mongos, который ещё не получил метку C, то в течение десятков миллисекунд он может увидеть согласованный снимок без перевода. Половину перевода он не увидит и в этом случае.

Чтобы закрыть все пути, которые проходят через систему, вводится **токен согласованности**:
- API возвращает в ответе на перевод operationTime транзакции, 12 Б.
- Приложение передаёт токен в следующих запросах. Сервис передаёт его в причинно-согласованную сессию драйвера (afterClusterTime), и чтение выполняется с меткой не меньше токена.
- Push о входящем переводе несёт метку события из change stream. В change stream попадают только изменения, подтверждённые majority [[32]](https://www.mongodb.com/docs/manual/changeStreams/). Боря, открывший приложение из push, видит деньги.

Сдвиг часов вперёд больше maxAcceptableLogicalClockDrift (по умолчанию 1 год) отвергается [[24]](https://dl.acm.org/doi/10.1145/3299869.3314049) |

| Записи oplog участника | applyOps с prepare: true (изменения и P_i), затем commitTransaction (C) или abortTransaction |

| Токен согласованности | 12 Б: метка операции в ответе API, в заголовке следующих запросов и в payload push |

#### 7.2.5. Альтернативные решения

| Способ | Пример | Откуда метка фиксации | Цена | Гарантия |
| --- | --- | --- | --- | --- |
| Системные часы шардов без согласования | - | часы каждого шарда | 0 | нарушается: при расхождении часов более позднее событие получает меньшую метку, и читатель не видит уже завершённый перевод |
| Оракул времени (Percolator) | TiDB [[29]](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Peng.pdf) | центральный сервис выдаёт метки начала и фиксации | 2 обращения к оракулу на транзакцию, для ДЦ-3 это +2 × 23 мс; оракул - выделенный узел с лидером в одном ДЦ | snapshot isolation |
| TrueTime (Spanner) | Google [[28]](https://www.usenix.org/conference/osdi12/technical-sessions/presentation/corbett) | системное время с известной погрешностью ε (1-7 мс); перед ответом транзакция выжидает, пока погрешность не пройдёт | ожидание порядка ε; GPS и атомные часы в каждом ДЦ | внешняя согласованность |
| Детерминированное планирование (Calvin) | YDB [[30]](https://ydb.tech/docs/ru/contributor/datashard-distributed-txs) | координаторы назначают транзакции глобальный шаг плана | шаг планирования; отдельные координаторы | сериализуемость. YDB отклонена в п. 6.5 |
| Сага: списание и зачисление - две локальные транзакции, связь через outbox | - | у каждой части своя | 2PC нет, задержка доставки события 0,1-2 с | атомарной видимости нет: «деньги в пути» видны клиенту и сверке; нужны компенсации, например возврат, если счёт получателя закрыли. Деньги в пути учитываются на транзитном счёте банка; один общий транзитный счёт стал бы горячим (п. 7.1), поэтому его пришлось бы делить по шардам |
| **HLC и C = max(P_i) (MongoDB, выбрано)** | MongoDB 4.2+ | максимум меток подготовки участников | 3 записи majority на фиксацию; читатели подготовленных документов ждут | snapshot isolation и причинная согласованность |

Правило «ждать, если на записи блокировка с меткой не больше метки чтения» общее для всех вариантов с подготовкой. В Percolator читатель так же ждёт блокировку с меткой из диапазона [0, R] [[29]](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Peng.pdf). Варианты различаются тем, откуда берутся метки.

#### 7.2.6. Обоснование выбора и параметров

**Почему выбран HLC с C = max(P_i):**
- Нет центрального узла и специального оборудования: метку назначают сами участники из своих часов. Это подходит для трёх равноправных ДЦ.
- Даёт атомарную видимость (требование 2), которой нет у саги, поэтому сверка и клиент никогда не видят «деньги в пути».
- Встроен в выбранную СУБД и проверен формально: протокол описан на TLA+ [[23]](https://www.vldb.org/pvldb/vol18/p5045-schultz.pdf).
- Цена - ожидание читателей на подготовленных документах в течение около 0,1 с. Для 137 переводов в секунду она приемлема. Отсутствие внешней согласованности закрывается токеном согласованности.

| Параметр | Значение | Обоснование |
| --- | --- | --- |
| writeConcern / readConcern транзакции | majority / snapshot (п. 6.6) | без majority запись prepare или решения может пропасть при выборах, и атомарность нарушится |
| Порядок команд | первой - запись на шард отправителя | координатор в ДЦ клиента: экономит межДЦ-обмен при передаче фиксации, в примере с отправителем в ДЦ-1 и получателем в ДЦ-3 около 35 мс |
| Изменения на шарде получателя | минимальные; для горячего счёта - только вставки (п. 7.1) | пока подготовленная транзакция не завершена, её документы заняты; вставки новых документов не блокируют остаток получателя |
| transactionLifetimeLimitSeconds | 60 с (по умолчанию) | ограничивает только неподготовленные транзакции; на подготовленные не действует |
| Таймаут перевода на стороне сервиса | 5 с, повтор с тем же ключом идемпотентности (п. 3.6) | повтор после неизвестного исхода не проведёт перевод дважды |
| Токен согласованности | operationTime в ответе API и в push | гарантирует, что следующий запрос клиента увидит его перевод |

#### 7.2.7. Влияние на физическую схему, нагрузку и взаимодействие

**Задержка фиксации перевода** (расчёт по RTT из п. 3.2):

| Перевод | Задержка | Из чего складывается |
| --- | --- | --- |
| Внутри одного шарда (1/64) | 15-30 мс | команды и одна запись majority |
| Разные шарды, primary в одном ДЦ (около 1/3) | 35-75 мс | команды и 3 записи majority по 9-23 мс |
| Разные шарды, primary в разных ДЦ (около 2/3), ДЦ-3 → ДЦ-1 | около 130 мс | 2 команды через межДЦ-канал (46 мс), список участников (23 мс), подготовка шарда 42 (32 мс), решение (23 мс) |

Все значения укладываются в 300 мс.

- **Занятость документов.** Документы счетов участников заняты от первой записи до фиксации, при переводе между ДЦ около 110 мс. Конфликт возникает с момента снимка транзакции, поэтому окно - 100-140 мс. Это определяет предел 7-10 зачислений в секунду на один счёт, который обходит п. 7.1.
- **Ожидание чтений.** Чтения, попавшие на подготовленные документы, ждут до 0,1 с. При отказе координатора - до времени выборов, 10-15 с.
- **Нагрузка на хранилище.** Межшардовый перевод добавляет около 7 служебных записей в oplog:
  - 3 записи координатора: список участников, решение, удаление;
  - по 2 записи на каждого из двух участников: prepare и commit.

  В пике это около 1 000 записей в секунду на кластер, около 15 на шард, то есть +13 % к 119 записям в секунду пика шарда (п. 6.6). В config.transaction_coordinators одновременно около 15 документов.
- **API и push.** Ответ на перевод и любые ответы с изменениями получают поле токена согласованности. Запросы принимают его в заголовке. Payload push содержит метку события.
- **Межсервисное взаимодействие.** Change stream отдаёт только изменения, подтверждённые majority, и только после фиксации [[32]](https://www.mongodb.com/docs/manual/changeStreams/). Push, поиск и сверка никогда не получают половину перевода.
